## Why this matters

Today the site answers "where can I go FROM here". Apartment hunters ask the
opposite: "I work at X - from which parts of the city can I still get to
work in 30 minutes?" That is a reverse (arrive-by) isochrone, listed on
`ROADMAP.md` as both "Reverse isochrone" and "Commute evaluator". The
routing engine only supports departure-based search, so this plan has two
halves: an `arrive_by` mode in the Rust isochrone server, and a focused page
at `/na-posao` where you pin your workplace and read the answer, with an
address checker for specific candidate homes.

## Steps

### Step 1: Understand and document the forward search (no code changes)

Read `compute_travel_times` (`isochrone_server.rs:320` onward) and write, in
the PR description or a code comment block, a half-page summary of its data
model: how patterns/stop-times are laid out, how boarding is found for a
departure time, how walk expansion seeds and finishes. This is the design
gate for Step 2. If per-stop schedule data is only indexed "next departure
after t" with no way to ask "latest arrival before t" without O(n) scans
per stop, note the cost.

**Verify**: the summary exists and names the exact structs/fields.

### Step 2: Implement `arrive_by` in the Rust server

Add `arrive_by: Option<String>` to `IsochroneParams` ("1" = on; absent = old
behavior; keep backward compatibility byte-for-byte for existing calls).
Semantics when on: `lat/lon` is the DESTINATION and `time` is the required
ARRIVAL time; the response's per-cell/per-stop values mean "travel time from
that place to the destination, arriving by `time`".

Implementation strategy: mirror the forward search backward in time - seed
the destination with the walk graph (walk times are symmetric), then relax
transit "in reverse": for each pattern serving a reached stop, find the
latest trip whose arrival at that stop is <= the stop's current latest-
departure bound, and propagate to UPSTREAM stops using that trip's earlier
scheduled times. Travel time for a place = arrival_time - latest_departure
from that place. Keep the same MAX_SECONDS cutoff, time snapping, and
response shape (so the client render path is unchanged). Skip GTFS-RT
overlay and bajs in v1 of the reverse mode: force `realtime=0` semantics and
ignore `bajs=1` when `arrive_by=1`, and say so in a comment (predicting
delays backward is a different problem).

**Verify**: `cargo build --release`, `cargo clippy -- -D warnings`,
`cargo test` → exit 0, including the new unit tests (Test plan). With the
local stack up: `curl "localhost:3002/api/isochrone?lat=45.813&lon=15.978&time=08:30&arrive_by=1&routing=0" | head -c 300`
returns the standard response shape; the same call WITHOUT `arrive_by`
returns the forward result unchanged (diff a saved fixture from before your
change).

### Step 3: Sanity-check symmetry

Add a Rust test (or an e2e script under `transit/` if unit granularity is
impossible): pick two points A (Trg-area) and B (a suburb). Forward from B
at 08:00 reaching A in T minutes implies reverse-from-A arriving 08:00+T
shows B reachable in approximately T (tolerance: a few minutes - headway
asymmetry is expected, but a 2x discrepancy means the reverse relaxation is
wrong).

**Verify**: test passes; record the two travel times in the test's assert
message.

### Step 4: Client params + /na-posao page

Extend `lib/otp.ts` `IsochroneParams` with `arriveBy?: boolean` mapping to
`arrive_by=1` in `buildIsochroneSearchParams` (`lib/otp.ts:18-26`).

Create `app/na-posao/page.tsx` + client components: a focused, single-
purpose page (not a /karta clone):

- Above the map: address search input ("Gdje ti je posao?") using
  `useAddressSearch` from `lib/use-address-search.ts`, plus an arrival-time
  select (07:00-10:00 in 30-min steps, default 08:30) and a 30/45-min
  window toggle.
- The map: reuse the smallest viable MapLibre setup (model on
  `app/promjene/diff-map.tsx` conventions rather than the full
  `map-canvas.tsx`) rendering the reverse walk-area GeoJSON with
  `reachColorStops()` from `lib/reach-ramp.ts`. Destination pin at the
  workplace.
- Below: "provjeri adresu" - a second address input; on select, call the
  same reverse response (or a point lookup within it) and print: "S adrese X
  stižeš na posao za ~N minuta" or an honest miss ("izvan 45-minutnog
  dosega"). If the response does not support point lookup cheaply, call the
  forward isochrone from the candidate address and read the destination
  cell - one extra request is fine.
- Metadata `pseoMetadata({ path: "/na-posao", ogType: "website", ... })`;
  title along the lines of "Odakle stižeš na posao javnim prijevozom".
  Add nav entry `{ label: "na posao", href: "/na-posao" }` and a sitemap
  line. All copy: kvart, no em-dashes, informal ti-form like the homepage.

**Verify**: `bun run typecheck && bun run lint && bun run test` → exit 0.
Dev flow: pick a workplace address → reverse area renders; check an address
inside the area → sentence with minutes; outside → honest miss. Toggling
arrival time changes the area.
